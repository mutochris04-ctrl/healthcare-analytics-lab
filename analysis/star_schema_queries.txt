QUESTION 1: Monthly Encounters by Specialty

SQL:
SELECT
    dim_date.year_and_month AS encounter_month,
    dim_specialty.specialty_name,
    dim_encounter_type.encounter_type_name AS encounter_type,
    COUNT(*) AS total_encounters,
    COUNT(DISTINCT fact_encounters.patient_key) AS unique_patients
FROM fact_encounters
JOIN dim_date           ON fact_encounters.encounter_date_key = dim_date.date_key
JOIN dim_specialty      ON fact_encounters.specialty_key = dim_specialty.specialty_key
JOIN dim_encounter_type ON fact_encounters.encounter_type_key = dim_encounter_type.encounter_type_key
GROUP BY encounter_month, dim_specialty.specialty_name, encounter_type
ORDER BY encounter_month, dim_specialty.specialty_name, encounter_type;

Execution time (Workbench): 0.141 s vs 0.094 s original
Execution time (test runs): 49-81 ms vs 47-63 ms original
Improvement: about the same speed with this amount of data
(0.7x to 1.3x depending on the run)

Explanation:
The query is simpler: the specialty is on the fact row (no
providers -> specialties chain) and the month is ready in dim_date
(no DATE_FORMAT). But it still joins 3 dimensions for all 30,004
rows, while the original joined only 2 very small tables
(9 providers, 4 specialties). With so few rows, both designs do
about the same work. The star schema's advantage here is simpler SQL
and an easy way to add more dimensions (age group, department...) with
one JOIN each. A speed gain may appear with much more data, but I did
not measure that, so I do not claim it.


QUESTION 2: Top Diagnosis-Procedure Pairs

SQL:
SELECT
    dim_diagnosis.icd10_code,
    dim_diagnosis.icd10_description,
    dim_procedure.cpt_code,
    dim_procedure.cpt_description,
    pairs.encounter_count
FROM (
    -- Step A: for every (diagnosis, procedure) pair of keys,
    -- count the DIFFERENT encounters that have it (same as the original)
    SELECT
        bridge_encounter_diagnoses.diagnosis_key,
        bridge_encounter_procedures.procedure_key,
        COUNT(DISTINCT bridge_encounter_diagnoses.encounter_key) AS encounter_count
    FROM bridge_encounter_diagnoses
    JOIN bridge_encounter_procedures
         ON bridge_encounter_diagnoses.encounter_key = bridge_encounter_procedures.encounter_key
    GROUP BY bridge_encounter_diagnoses.diagnosis_key, bridge_encounter_procedures.procedure_key
) AS pairs
-- Step B: add the codes and names
JOIN dim_diagnosis ON pairs.diagnosis_key = dim_diagnosis.diagnosis_key
JOIN dim_procedure ON pairs.procedure_key = dim_procedure.procedure_key
ORDER BY pairs.encounter_count DESC
LIMIT 10;

Execution time (Workbench): 0.156 s vs 0.703 s original
Execution time (test runs): 88-104 ms vs 297-349 ms original
Improvement: about 3-4x faster

Explanation:
The pairs are still many-to-many, so the bridge tables still create
89,951 pair rows. What changed:
- Step A counts the DIFFERENT encounters for each pair using only small
  whole-number keys, from bridge tables whose primary key starts with
  encounter_key. COUNT(DISTINCT encounter_key) is the same metric as
  the original COUNT(DISTINCT encounter_id).
  (I checked: for all 38 pairs, COUNT(*) and COUNT(DISTINCT ...) give
  the same number, because a bridge table cannot hold the same
  diagnosis or procedure twice for one encounter. I still use DISTINCT
  so the query says exactly what it counts.)
- Step B looks up the codes and names only for the 38 different
  pairs, instead of for 89,951 rows.
Honest note: I tested the same two-step trick on the original
database too, and it took about 180 ms. So a large part of the gain
comes from the better query, and the rest from the star schema's
compact key-only bridge tables.


QUESTION 3: 30-Day Readmission Rate

SQL:
SELECT
    dim_specialty.specialty_name,
    COUNT(*) AS inpatient_stays,
    SUM(fact_encounters.is_readmitted_30_days) AS readmitted_stays,
    ROUND(100 * SUM(fact_encounters.is_readmitted_30_days) / COUNT(*), 2) AS readmission_rate_percent
FROM fact_encounters
JOIN dim_specialty      ON fact_encounters.specialty_key = dim_specialty.specialty_key
JOIN dim_encounter_type ON fact_encounters.encounter_type_key = dim_encounter_type.encounter_type_key
WHERE dim_encounter_type.encounter_type_name = 'Inpatient'
GROUP BY dim_specialty.specialty_name
ORDER BY readmission_rate_percent DESC;

Execution time (Workbench): 0.016 s vs 0.125 s original
Execution time (test runs): 7.5-8.6 ms vs 66-109 ms original
Improvement: about 8-15x faster (the biggest gain)

Explanation:
No self-join. The ETL already checked every inpatient stay once and
stored the answer in is_readmitted_30_days (1 or 0). The query just
filters inpatient stays and adds up the 1s with SUM(). The expensive
date comparisons happen once per load, not every time the report runs.
The ETL check proves the flag follows the same rule: 502 readmitted
stays in both databases.

Result: Clinical Nutrition has the highest readmission rate
(16.24%), then Cardiology (5.09%) and Internal Medicine (4.87%).
Emergency has no inpatient stays.
Data limit: the 276 inpatient stays discharged in December 2025 do not
have 30 full days of follow-up in the data, so their rate is
underestimated (in both databases).


QUESTION 4: Revenue by Specialty & Month

SQL:
SELECT
    dim_specialty.specialty_name,
    dim_date.year_and_month AS encounter_month,
    SUM(fact_encounters.total_allowed_amount) AS total_allowed
FROM fact_encounters
JOIN dim_specialty ON fact_encounters.specialty_key = dim_specialty.specialty_key
JOIN dim_date      ON fact_encounters.encounter_date_key = dim_date.date_key
WHERE fact_encounters.bill_count > 0
GROUP BY dim_specialty.specialty_name, encounter_month
ORDER BY dim_specialty.specialty_name, encounter_month;

Execution time (Workbench): 0.094 s vs 0.188 s original
Execution time (test runs): 42-73 ms vs 72-73 ms original
(total per specialty without months: 19-34 ms vs 51-84 ms, about 2.5-3x faster)
Improvement: about the same to 1.7x faster

Explanation:
The money (total_allowed_amount) is already on the fact row, and
specialty_key too. So the 3-join chain billing -> encounters ->
providers -> specialties becomes 2 small joins (specialty and date),
and the month comes ready from dim_date. The gain is bigger for the
total per specialty, because it needs only 1 join.
WHERE bill_count > 0 keeps only encounters that have a bill, exactly
like the original query, which starts from the billing table. Without
it, the 2 encounters with no bill (7003 and 7004) would be included
with 0. Today that changes no number, but the filter makes the two
queries equal by design, not by luck.
